## Gate r2 fix (`fix: STORY-007 - gate r2: a sheet deleted after its render is 410, never 500`)
Review finding (`docs/findings/STORY-007-review.md` round 2): `get_sheet` ran `settled` BEFORE reading the rendered PNG, so a DELETE between the two made `_cached` return None → 500 `preview_failed` instead of 410.
- **Route** (`src/pdf_splitter/routes/preview.py` `get_sheet`): after a render the bytes are read FIRST (`_cached`), then `settled` re-checks the row, and only then does a missing file become 500. So whenever the bytes are missing (render reported `gone`, the file vanished, `_cached` None) the row has been re-checked after the read: deleted/expired → 410 `expired` (and `settled` removes whatever raced in); only a live job gets 500 `preview_failed`. A DELETE after the read serves the bytes already in hand (200) and still leaves nothing on disk (the DELETE's own `rmtree`). `post_section_plan` already had this order: the subprocess result is in memory before `settled` runs, and a missing `analysis.json` goes through `settled` too — unchanged.
- **Tests** (`tests/test_api_e2e.py`, "Gate r1" block), both run against `3058d91`'s `routes/preview.py` and confirmed failing there with 500 `preview_failed` (`2 failed`), passing with the fix: `::test_a_sheet_deleted_between_its_render_and_the_read_is_410_not_500` (the real subprocess renders; a hook on `_cached`'s post-render call runs the real DELETE first → 410, no `<jobs>/<id>`) and `::test_a_sheet_deleted_after_the_row_check_is_served_not_500` (the reviewer's deterministic settled-then-delete hook, `scratchpad/rv007g2/fix/tests/test_zz_probe.py`). **Deviation:** the reviewer's probe asserted 410 for that hook, but with bytes-first ordering (which the fix instruction requires) the DELETE lands after the PNG was read and after the row was found live, so there is nothing left to re-check: the correct outcome is 200 with the rendered PNG, row `deleted`, no directory. ## Decisions (small ambiguities resolved)
- **"Names deduped" = normalized, not rejected.** Architecture § Data Types says duplicates are allowed in the UI and PUT returns the "normalized Plan", so the saved plan gets `Name (2)`, `Name (3)` (truncating the base to stay ≤ 120). ZIP entries and engine names are unique by the `NNN` prefix regardless.
- **Error codes** (all in `src/pdf_splitter/errors.py:MESSAGES`, one table, `upload.py` imports it): `not_found` (404: unknown job, a sheet/section index out of range, an unrouted path), `expired` (410: deleted or past its TTL), `not_ready` (409: analysis/plan/previews before `review`, downloads before a cut, PUT/cut from `failed`), `busy` (409: PUT plan or POST cut while a job is queued/running), `invalid` (422 + `errors[]`; also the router's 405), `preview_failed` (500, expected: a preview subprocess timed out or crashed), `internal` (500 + `request_id`, unexpected). The STORY-005 upload codes are unchanged.
- **"Analyzed" = `state ∈ {review, done}` or `kind == "cut"`** (`routes/common.py:35`): a queued, running or failed cut still has its analysis and plan, so GET analysis/plan and the previews work then; PUT plan and POST cut need `review` or `done` (409 `busy` while queued/running, `not_ready` from `failed`).
- **Section PDFs are served out of `result.zip`**, not from `work/`, and `manifest.json` lives only inside the zip: the zip is the one artifact a cut replaces whole (Architecture § Job states: old outputs stay downloadable until the next cut replaces them), so `sections/{i}.pdf` and `result.zip` can't disagree and a running re-cut can't take a download away. `i` is the PLAN index the zip was cut from; the manifest carries it. Rows not written by the engine (a plan that falls off the book) are simply absent → 404.
- **The Section plan's `rects` name the absolute 1-based sheet** (the engine's `rects()` gives the index within the excerpt); Architecture's `rects:[[sheet,[x0,y0,x1,y1]]]` doesn't say which, and the UI draws over `/sheets/{n}.png`. `notes` is included next to `flags`.
- **The PNG cache is keyed on the SAVED plan's settings hash** as AC-2 and the file layout say, although the pixels don't depend on settings (the overlay is the UI's), so a settings change costs one re-render per sheet (≈ 0.2–0.6 s), never a re-index. Rendering uses PyMuPDF directly in the preview subprocess (Architecture § Engine additions allows fitz for PNG rendering); `Book.sheet_png` would have needed a Book and therefore possibly a 12 s re-index for a picture.
- **Override cut bounds:** `startCut ≤ H` of the section's first sheet; `endCut ≤ max(H)` over the book, because the last sheet is only known after planning. Cuts are ≥ 0.
- **`Override` keeps only the keys the client sent** (`model_fields_set`), because the engine's `apply_overrides` applies present keys: `startCut: null` removes the cut, an absent `startCut` keeps the engine's. `startCol`/`endCol` default to `full` only when set without a value.
- **`POST /cut` on an empty plan is 422** (`errors: [{loc: ["plan", "sections"]}]`) rather than a job that produces a zip with only a manifest.
- **`queue_position` is `null`** (STORY-012 owns it, per the kickoff's scope); the key is present so the SPA's type is stable.
- **`Store.transition` accepts several `expect` states, a `kind`, and zeroes `progress`/`total` when the new state is `queued`**, so the row a cut is queued on doesn't show the analyze's 1319/1319 until the task's first tick. The worker's re-queue (`recover`) goes through the same path, which is right (a re-run starts from zero).
- **`default_plan` caps names at 120 and headings at 500** (`analyze.py:36`), so the plan the analyze task writes is always one a client can PUT back unchanged (an outline title longer than 120 chars would otherwise be a 422 the user never typed).
- **`upload.MESSAGES` became `errors.MESSAGES`** (tests still read `upload.MESSAGES`); the preflight's own codes are `upload.PREFLIGHT_CODES`. `runner.loggable_tail`/`STDERR_TAIL` moved to `access_log.py` (the API's 500 path needs them and `runner` already imported `access_log`); `task._write_json` became `files.write_json` (the API writes `plan.json` with it too).
- **The preview subprocess reads its request from stdin** (`subprocess.run(input=…)`) instead of argv: the section list is the whole plan. The job dir is still the `--`-guarded positional, so a dash-leading id is fine; `tests/test_api_e2e.py` runs every route under `DASH_ID`.
- **A preview that fails is 500 `preview_failed`, not `internal`**: it is an expected outcome of a hostile page (timeout, rlimit) and carries no request id in the body; the API logs `log_id` + the redacted stderr tail.

## Handoff Context for Next Session
Every endpoint's status codes and body shapes are pinned by `tests/test_api_e2e.py` (see the AC list above for the test per route) and the error codes by `src/pdf_splitter/errors.py:MESSAGES`; STORY-008's `errors.ts` should be generated from that table (13 codes). The SPA polls `GET /api/jobs/{id}` while `state ∈ {queued, running}`; `review`/`done`/`failed` are terminal for that poll, 410 means deleted/expired, and `error_code` is only ever non-null with `failed`. A preview (`sheets/{n}.png`, `sections/{i}/plan`) can answer 410 even when the job was live when the request went out (a DELETE landed during the render, § Gate r1 fix): treat 410 from any route as "the job is gone", not as a preview failure. The dev proxy target is the API's port (`pdf-splitter api --port 8010` on this laptop; the story says :8000, which is taken here). A plan whose `settings` differ from the index's makes the FIRST preview (`sections/{i}/plan`) re-index the book inside the 20 s window (12–14 s for 1319 pages on this laptop; a slower VM or a bigger book will time out → `preview_failed`), and the following previews are fast again; sheet PNGs never re-index.
