## Decisions (small ambiguities resolved)
- **No engine change; progress via an iterator wrapper.** v0.4.1's `index_book` runs `[index_page(page, prof) for page in book]`, so `analyze._Counted` wraps the document, and its `__iter__` reports page *i* when the engine asks for page *i+1* (that is, after page *i* is indexed). The engine's own cache key and file format are kept, not copied. The engine hook is still the right long-term fix (see Out-of-Scope). If a future engine indexes by `book[i]` instead of iterating, progress silently stops moving but correctness is unaffected. `_Counted` also forwards `__getitem__`/`__getattr__`.
- **Sandbox = launcher + exec, not `preexec_fn`.** The runner spawns from `WORKERS` threads, and `preexec_fn` is not safe in a threaded parent. `worker/sandbox.py` sets its own limits, then `execv`s `sys.executable` with the job's args, and only ever this interpreter. The preflight (spawned from the API's threadpool) can't take the launcher without changing its argv shape (its STORY-005 tests pin `cmd[:3]`), so it takes an opt-in `--cpu-limit S` and applies the same `sandbox.apply` itself before opening the file. It is opt-in so tests that call `preflight.main()` in-process don't limit the test runner.
- **Process group.** `start_new_session=True` + `killpg(SIGKILL)` on timeout, so anything the task spawned dies with it (`::test_runner_timeout_kills_the_whole_process_group`).
- **Resources vs internal.** Only SIGXCPU/SIGKILL/SIGXFSZ (and the kernel OOM killer's SIGKILL) and the task's own `resources` result count as resources. SIGSEGV/SIGABRT count as `internal`, because a MuPDF crash is not proof of a limit. Under RLIMIT_AS, Python allocations raise `MemoryError`, which `guarded` maps. MuPDF allocates outside Python and PyMuPDF 1.28.2 has no memory-error class, so its allocator failing arrives as a plain `RuntimeError("code=2: calloc (…) failed")`; the gate r1 fix maps that by message (see below), and every other `RuntimeError` stays `internal`.
- **Who writes the final state.** The task moves `running → review` itself (conditional on `running`). The runner writes every failure (also conditional), and treats "exit 0 but the row is still running" as `internal`.
- **Re-queue marker (no schema change).** `error_code='requeued'` on a `queued`/`running` row. `message` couldn't carry it, because `update_progress` overwrites `message`. STORY-007: `GET /api/jobs/{id}` should expose `error_code` only when `state == 'failed'`, or the UI must key on `state`. A twice-stale job fails as `timeout`.
- **Periodic sweep (beyond the AC's "on start").** Taken literally, a job orphaned by a quick restart (younger than its timeout at start) would sit in `running` forever. The loop therefore repeats the sweep every 30 s, skipping this process's in-flight ids.
- **Default plan settings = `WEB_BASE` values** (`column_split 0.487, single_column false, header_band 50, footer_band 32, heading_min_size 12.5`). The analyze index is built under exactly this profile, so the cut or preview of an unchanged default plan reuses `work/.book-index.json`. I did not adapt `heading_min_size` to the suggested level's size: that would change the profile hash and force a full re-index on the first preview. Below 12.5 pt, `locate_heading` still matches single-line headings exactly.
- **`analysis.outline.levels`** = counts for levels 1..deepest present (≤ 3), with 0 for a gap; `[]` = no outline. `items` = level 1 rows, then level 2, then level 3, each in outline order.
- **Progress total = page count.** The heading pass (≈ half the wall time on Maciocia: 13 s of 27 s) has no page ticks; the row shows `Finding headings` at `total/total`.
- `SIGTERM`/`SIGINT` set the stop event: loops stop claiming, and in-flight jobs finish (or the container's kill cuts them, and the next start's sweep re-queues them).

## Gate r1 fixes (`e15e7f0`, review: `docs/findings/STORY-006-review.md`)
Two confirmed findings, fixed forward in one commit on top of the story. Both were reproduced first with the reviewer's own scripts (`rv006/mkbombs.py` → `xbomb6.pdf`, `probe_mupdf_oom.py`, `probe_surrogate*.py`), and both builders now live in `tests/fixtures/hostile.py` (byte-for-byte PDFs, because PyMuPDF would normalise exactly what the tests need).

1. **MuPDF allocation failures are `resources`** (finding 1, AC-4). Under RLIMIT_AS the reviewer's 4.9 KB nested-XObject bomb (page 2 draws 10 × 10 × … Form XObjects, 6 deep = 10^6 glyph runs) makes MuPDF's own allocator fail inside text extraction. That is not a Python `MemoryError`: PyMuPDF 1.28.2 raises FZ_ERROR_SYSTEM as a plain `RuntimeError("code=2: calloc (4104 x 1 bytes) failed")` (VmPeak = the 2 GB cap, ~7 s), and `guarded` sent it to `internal`. `worker/task.py:34` `MUPDF_ALLOC_FAILED` matches a message that starts with `code=2` (FZ_ERROR_SYSTEM), or names `calloc`/`malloc`/`realloc` … `failed`, or says `out of memory`, case-insensitively; `guarded` (`task.py:110`) maps a `RuntimeError` matching it to `resources` (exit 3) and leaves every other `RuntimeError` (a format error, `code=3: load failed for object`, a path that merely contains `code=2`) as `internal`. Only `RuntimeError` is inspected: the same text in a `ValueError` stays `internal`. Contracts: `tests/test_worker.py::test_real_task_on_a_mupdf_memory_bomb_is_resources` (the reviewer's bomb through the real sandbox launcher and `Runner.run_once` → row `failed/resources` with the user-facing message, no `analysis.json`, no `.tmp`, the id hashed in the log; ≈ 8 s and 2 GB RSS in the child), and `::test_guarded_maps_exceptions` (9 new message cases, 5 mapped and 4 deliberately not).
2. **`analysis.json`/`plan.json` survive text that is not valid Unicode** (finding 2). PyMuPDF decodes a malformed text string with `surrogateescape`, so a bookmark title such as `<EFBBBF4368617074FF6572>` (UTF-8 BOM + a `0xFF` byte) comes back as `'Chapt\udcffer'` and `<FEFF00430068D800>` (a trailing lone high surrogate, re-encoded CESU-style) as `'Ch\udced\udca0\udc80'`. `json.dumps(ensure_ascii=False)` was fine with those, but the strict UTF-8 `write_text` raised `UnicodeEncodeError`: the whole analysis became `failed/internal` and an empty `analysis.json.tmp` stayed behind. Now `worker/analyze.py:73` `clean_text` replaces every lone surrogate with U+FFFD (one per code unit, so the rest of the title survives: `Chapt�er`, `Ch���`), and `analyze.py:78` `json_safe` applies it to every string, value or key, in the analysis dict at the ONE place engine/PyMuPDF strings enter it (`analyze.py:122`, before `suggest`). `default_plan` derives from that dict, so the plan's section names are clean with no separate step, and so is anything STORY-007 builds from `analysis.json`. `_write_json` (`task.py:66`) is the backstop: it encodes with `errors="replace"` (a string that dodged `json_safe` costs a `?`, never the file) and removes the `.tmp` on any failure, including a non-serialisable value, so the previous file is left intact. Contracts: `::test_task_survives_a_bookmark_title_that_is_not_valid_unicode` (both review byte sequences through `task.main` → `review`, `analysis.json` and `plan.json` decoded strictly, the names above, `plan == default_plan(analysis)`, no `.tmp`), `::test_json_safe_replaces_every_lone_surrogate_and_nothing_else` (CJK, dashes, emoji untouched; the uncleaned dict still fails strict UTF-8), `::test_write_json_never_fails_on_encoding_and_leaves_no_tmp`.

Re-verified with the reviewer's scripts after the fix: `probe_bombs.py … xbomb6.pdf` through the real `Runner` logs `job a48d2946 analyze failed: resources (exit 3)` and the row reads `failed/resources`; the two surrogate titles analyze, write, and leave no `.tmp` (`sur.py`, the two cases from `probe_surrogate2/4.py`).
